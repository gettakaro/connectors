## 5. C4 queues

| Queue | Type / capacity | Admission | Drain | Timeout | Shutdown |
|---|---|---|---|---|---|
| DbWriter `_queue` | `BlockingCollection<Action>`, **unbounded** (`DbWriter.cs:42`) | Always accepted. Above `QueueDepthWarnThreshold = 1000` (`DbWriter.cs:18`), **every** enqueue logs a Warn, and each Warn is a synchronous file open/append/close on the producer thread, usually main (`DbWriter.cs:52-53`, `LogService.cs:86-112`). Check-then-`Add` is racy against `CompleteAdding` (`DbWriter.cs:49-55`). | One thread, one op at a time under `Database.SyncRoot` (`DbWriter.cs:76-96`). No batching. | None | `CompleteAdding`, then `Join(5 s)` (`DbWriter.cs:98-103`). On timeout, `Database.OnDestroy` disposes the DB **without taking SyncRoot** (`Database.cs:59-63`), so a still-running writer can hit a disposed DB. |
| MainThreadDispatcher `_queue` | `ConcurrentQueue<Action>`, **unbounded** (`MainThreadDispatcher.cs:20`) | Rejected only when `_shuttingDown` (`MainThreadDispatcher.cs:44-48`). No depth limit and no rate limit. | `MaxOpsPerTick = 32` per `ModEvents.GameUpdate` (`MainThreadDispatcher.cs:18,81-82`). **No time budget**, so one slow op such as `RefreshBans`, called inside ban/unban (`ActionHandlers.cs:273,369`), is unbounded. | **None.** The awaiting `Dispatch` has no timeout (`RequestRouter.cs:322-365`). A request Takaro has already timed out still runs and still sends a late response. Captures are managed closures, so there is no lifetime hazard. | `Shutdown()` drains **every** queued op synchronously on the main thread with no cap (`MainThreadDispatcher.cs:91-96`). A `Run` that passes the `_shuttingDown` check just before the drain can enqueue after it, and its Task never completes (`MainThreadDispatcher.cs:44-60`). |
| Outbound `_outbound` (ingress) | `BlockingCollection<OutboundLedger.Entry>`, **unbounded** (`WebSocketTransport.cs:140`) | Always accepted. JSON is built by the caller (`WebSocketTransport.cs:188-207`). | Sender thread takes **1 entry per loop iteration**, then `FlushPending` writes the whole ledger synchronously (`WebSocketTransport.cs:225-253,340-434`) | `SENDER_POLL_MILLISECONDS = 1000` (`:110`). There is no send timeout. | `CompleteAdding`, then `Join(5 s)` (`WebSocketTransport.cs:183-185`) |
| OutboundLedger pending | `LinkedList`, `MAX_PENDING_MESSAGES = 500` (`WebSocketTransport.cs:104-108`) | Over the cap, the **oldest is dropped**, whatever its type: event, response or ping (`OutboundLedger.cs:217-225`). Seq is assigned before trimming, so v1 streams get gaps (`OutboundLedger.cs:92`). | Head-of-line. After 3 failures the head is dropped (`WebSocketTransport.cs:111,415-426`). | — | Lost |
| OutboundLedger in-flight | Max 500 (`OutboundLedger.cs:116-117`) | Oldest unacked entry is evicted silently | — | — | Lost |
| `_sendLock` | One lock. Writes are synchronous `socket.Send` (`WebSocketTransport.cs:392-397`), and identify is also sent under it from the receive thread (`:518-528`). | — | — | None | — |

**Growth despite the downstream cap: yes (DTD-2).** While `socket.Send` is blocked inside `FlushPending` (a slow receiver or a full TCP buffer), the sender thread does not return to `TryTake`. `_outbound` then keeps growing without limit from every producer, including the per-line log event feed (`API.cs:255-274`). The 500-entry cap applies only after `Buffer()` (`WebSocketTransport.cs:256-273`). The inbound-staleness watchdog bounds this to roughly 45 s, but only if the watchdog is reached, and it runs on the same blocked sender thread (`WebSocketTransport.cs:248,83`). The heartbeat timer also calls `CheckInboundLiveness` (`:786`), which can `CloseAsync` the socket.

**Shutdown order** (`API.cs:74-87`, `ServiceRegistry.cs:41-55`):
1. `MarkGameStopping`.
2. Unregister `GameMessage` and the log callback.
3. Dispatcher drain. The responses it produces are enqueued while the socket is still open.
4. `ConfigManager.StopWatching`.
5. Transport `Shutdown`: synchronous `Close` (`WebSocketTransport.cs:941`), then `CompleteAdding`, then join 5 s. Ledger contents are discarded, and unacked events are not persisted.
6. Services destroyed in reverse order: PositionSampler, Dispatcher (no-op), StateMirror (no-op), DbWriter join 5 s, Database dispose, LogService.

Race: the `WhenDrained` callback checks `_gameShuttingDown` and then calls `Initialize` on the thread pool (`API.cs:55-65`), so it can start the sender thread after shutdown has begun.

## 7. C6 delivery

| Aspect | Behaviour | Ref |
|---|---|---|
| Outbox bound | Pending 500 plus in-flight 500, drop-oldest. The ingress `_outbound` is unbounded. | `WebSocketTransport.cs:104-108,140` |
| v0 ack | A pong confirms events written before its ping (only on the same socket generation). An ack ping is sent at most once per second, and the heartbeat runs every 15 s. | `OutboundLedger.cs:138-154`, `TransportSession.cs:253-257`, `WebSocketTransport.cs:79,86` |
| v1 ack | `eventAck {streamId, upTo}` is cumulative and removes from both in-flight and pending | `OutboundLedger.cs:162-190`, `TransportSession.cs:177-183,259-260` |
| eventError | Logged only. The comment says an "internal" error closes the socket and the event is resent. | `WebSocketTransport.cs:681-700` |
| Reconnect replay | Unconfirmed in-flight entries go back to the head of pending on a new generation, giving at-least-once delivery | `TransportSession.cs:267-273`, `OutboundLedger.cs:198-215`, `WebSocketTransport.cs:354-361` |
| Responses | Not replayable, so they are lost on reconnect | `WebSocketTransport.cs:197-205` |
| Dead link | No inbound frame for 45 s closes the socket. Backoff is capped at 60 s. Identify deadline is 30 s. | `WebSocketTransport.cs:66-83,807-842,853-896` |
| Game crash | Everything is lost: the ledger, `_outbound` and the stream. The new process opens a new `StreamId`. No player-disconnected events are sent for players online at the crash, and the mirror starts empty. | `OutboundLedger.cs:52`, `API.cs:99` |
| Overflow priority | The log-event feed shares the 500 cap, so a burst of log lines evicts player events | `API.cs:255-274`, `OutboundLedger.cs:217-225` |

Conclusion: nothing is byte-copied. The common v1 behaviour (identify reply parsing, stream framing, eventAck) is re-implemented per runtime. A shared module is only realistic between Valheim and 7D2D, and their JSON libraries differ. Prefer shared acceptance fixtures (`tests/fixtures/generic-protocol.json`) over extracting code.
