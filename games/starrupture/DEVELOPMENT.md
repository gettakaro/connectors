# StarRupture connector: development

The connector is one ModLoader plugin, `TakaroStarRupture.dll`, inside the Windows dedicated server. It
holds the Takaro WebSocket itself. There is no sidecar and no inbound port.

```
mod/src/takaro_link.*          the Takaro connection: identify, requests, events, shutdown order
mod/src/takaro_protocol.*      portable protocol layer: capabilities, frames, argument checks, event stream
mod/src/net/                   WinHTTP WebSocket transport (async, heartbeat, backoff) and a small JSON reader
mod/src/plugin*.{h,cpp}        plugin entry, config, lifecycle, the player snapshot and the action queue
mod/src/starrupture_*.{h,cpp}  game logic against the Game SDK: players, items, teleport, bans, chat, combat
mod/src/modloader_process_events.*  the ProcessEvent observer behind chat and combat events
mod/src/game_icon.*            generated by mod/scripts/gen-icon.py from assets/icon-256.png
mod/tests/                     native tests against fakes, no game needed
scripts/build-release.sh       the release build, driven by catalog/starrupture/targets/<target>.json
```

## Threads

Takaro traffic runs on the plugin's worker thread. `getPlayers`, `getPlayer`, `getPlayerLocation` and
`getPlayerProgression` answer from a snapshot, refreshed on the game thread every 2 s, so they never wait
for a frame. Everything that touches game objects goes through the action queue, which the engine tick
drains under a limit.

## Build and test

```
docker run --rm -v "$PWD/games/starrupture/mod:/m" -w /m gcc:14 bash scripts/run-native-tests.sh
just build-release-starrupture 0.0.0-dev
```

The release build cross-compiles with clang-cl in the pinned image. The Plugin SDK and Game SDK are fetched
at the commits in the catalog target and never committed or packaged.

## A new game build

ModLoader refuses any game build but its own, and the Game SDK is generated per build. A new game build
therefore needs a matching ModLoader and Game SDK, then a new catalog target, then a live retest.
