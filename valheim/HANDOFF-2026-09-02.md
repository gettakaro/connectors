## Part 2 — inventory delivery (built, NOT live-tested)

`feat(valheim)!: deliver giveItem into the player's inventory` — protocol 2.

Server fires an `item-grant` and does not wait. The companion inserts what fits and drops
only the shortfall, telling the player in chat. Players without a companion keep the
server-side world drop unchanged.

**Why the server cannot wait** (this is the load-bearing constraint — do not "improve" it
into a round trip): `TakaroRequestDispatcher` blocks the Unity main thread via
`GetAwaiter().GetResult()` inside `QueuedMainThreadActionScheduler.Drain()`, and
`ValheimTakaroPlugin.Update()` runs `Drain()` *before* `companionBridge.Update()` on that
same thread. A companion reply arrives on a later frame, so awaiting it means `Drain()`
never returns and the dedicated server hangs permanently.

**Why delivery is counted, not assumed**: `Inventory.AddItem` partially fills — it adds
stackable units one at a time and, when it runs out of room, returns failure while keeping
what it already deposited. The companion counts the item before and after and drops the
difference. That accounting lives in `CompanionItemGrantMath` (pure, Unity-free, unit
tested in `CompanionItemGrantTests`).

## Rules that bit this session

- **Never modify takaro-core.** The shop's currency/refund behaviour lives there
  (currency deducted at order creation, order marked COMPLETED before delivery, delivery
  errors swallowed with no refund). Report it, do not patch it.
- Several contract tests read `.cs` files as **text** and slice method bodies between
  string markers. `TrySendItemGrant` must stay *after* `ForwardAcceptedEvent`, and
  `DropItemStack` must stay textually inside `GiveItemAsync`.
- `dotnet test` alone is not enough — it builds reference-free. Building against the real
  Valheim assemblies caught two compile errors this session that the test build could not.
